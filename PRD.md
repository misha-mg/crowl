# Crowl PRD и план реализации

Статус: первая реализация и расширение для одновременных сессий подготовлены. Базовую Telegram-переписку подтвердил пользователь; новые сценарии ожидают живой приёмки. Дата: 28 октября 2026. Фактические результаты: [VERIFICATION.md](VERIFICATION.md). Ограничение одного run на проект и запрет переключения во время работы из первоначального плана заменены решениями [ADR 002](docs/ADR-002.md).

Crowl — переносимый Telegram-интерфейс к локальным Claude Code и Codex. Пользователь помещает репозиторий в `.crowl` внутри рабочего проекта на Mac Mini, заполняет `.env` и запускает Crowl. Бот работает с файлами родительского проекта и сохраняет отдельные сессии агентов.

## 1. Границы первой версии

- Только macOS на постоянно работающем Mac Mini, один владелец.
- Один экземпляр `.crowl` → один проект → один токен бота → один приватный Telegram-чат.
- Несколько проектов обслуживаются независимыми процессами. Общий сервер, реестр проектов и межмашинная маршрутизация не нужны.
- Claude Code и Codex установлены и авторизованы локально. Отсутствие одного не мешает использовать другой.
- Текстовые и голосовые сообщения, выбор провайдера, сохранение сессий, остановка работы, просмотр и изменение режима разрешений.
- Начальный режим обоих провайдеров — полный доступ в пределах возможностей локального CLI и политик устройства.
- Foreground-запуск и необязательная установка пользовательского LaunchAgent.

За пределами версии: WSL, другие устройства, группы и topics Telegram, несколько пользователей, веб-панель, ACP, совместная работа агентов, автоматический handoff Claude ↔ Codex, голосовые ответы, произвольный удалённый терминал, импорт всех CLI-сессий, параллельное выполнение задач в одном проекте, автоматические commit/push/deploy. Сам агент выполняет разрешённые пользователем задачи по своим настройкам; Crowl не добавляет отдельные Git-ограничения.

## 2. Установка и пользовательский контракт

```bash
cd /path/to/your/project
git clone https://github.com/misha-mg/crowl.git .crowl
cd .crowl
npm ci
cp .env.example .env
# заполнить .env
npm start
```

`npm start` запускает TypeScript напрямую на Node.js 24, отдельная сборка не требуется. Зависимости и lockfile принадлежат Crowl; package.json рабочего проекта не изменяется.

Обязательная конфигурация:

```dotenv
TELEGRAM_BOT_TOKEN=
TELEGRAM_USER_ID=
```

Необязательная:

```dotenv
DEFAULT_PROVIDER=codex
DEFAULT_PERMISSION_MODE=full
VOICE_ENABLED=true
WHISPER_BIN=
WHISPER_MODEL_PATH=
CLAUDE_BIN=
CODEX_BIN=
```

`WHISPER_BIN` и модель могут быть автоматически найдены в стандартном локальном кеше. Для голоса нужны локальные whisper.cpp, FFmpeg и модель; это дополнительная подготовка, а не скрытое следствие двух переменных Telegram. `voice:setup` устанавливает/проверяет компоненты и скачивает многоязычную модель по явному запуску команды. Если нет необходимого установщика, команда даёт конкретную инструкцию и не сообщает об успешной готовности. Без компонентов текст работает, а голос возвращает понятную инструкцию. Никаких облачных STT-ключей в первой версии.

Рабочая директория вычисляется от расположения установленного Crowl: `realpath(<crowl root>/..)`. Текущая директория запуска не влияет на выбор проекта. Корень установленного пакета определяется до перехода к `dist`, а не как родитель произвольного исполняемого JS-файла. Отсутствующая директория или установка вне ожидаемой структуры дают ошибку, а не fallback в домашнюю папку.

Новый проект получают чистым клонированием `.crowl`, без `.env` и `.data`. Перенос существующего экземпляра требует остановки, повторной привязки к пути и переустановки сервиса; автоматический перенос нативных сессий не обещается.

`.env`, `.data/`, логи и временное аудио исключаются из Git Crowl. В родительском Git-проекте при setup предлагается локальное исключение `.crowl/` через `.git/info/exclude`, без изменения общего `.gitignore`. Обычный `npm start` чужие файлы не меняет.

## 3. Пользовательские сценарии

### Первый вход

1. Владелец создаёт бота в BotFather и записывает токен и свой числовой ID в `.env`.
2. Crowl проверяет конфигурацию, доступность Telegram и CLI, захватывает блокировку экземпляра.
3. Владелец отправляет `/start` в приватном чате. Проверяются `from.id` и тип чата; разрешённый chat ID сохраняется.
4. Бот показывает проект, доступных провайдеров и кнопки `Claude`, `Codex`.
5. После выбора создаётся логическая сессия. Нативный диалог может создаваться лениво при первом сообщении.

Проверки владельца выполняются для сообщений, голосовых, команд и callback-кнопок до скачивания файлов и запуска агентов. Сообщения посторонних не запускают никакие операции. Бот не привязывается к первому произвольному отправителю.

При запуске проверяются bot ID и наличие webhook. Чужой активный webhook не удаляется автоматически: Crowl объясняет конфликт. Telegram 409 от другого poller приостанавливает экземпляр с диагностикой, а не вызывает бесконечную борьбу процессов за токен.

### Обычная работа

Текст сохраняется локально до подтверждения получения Telegram update. Пользователь получает краткий статус и поток доступных сообщений агента. Итог сохраняется отдельно от прогресса. Ответ содержит результат, а ошибки не выдаются за успешное завершение.

Если агент занят, сообщение ставится в видимую очередь. Очередь FIFO, максимум 20 ожидающих сообщений, без неявного объединения промптов. Очередь хранит конкретный session ID на момент приёма, а не вычисляет его позднее из активной сессии.

### Голос

`Telegram voice → локальный OGG/Opus → FFmpeg WAV 16 kHz mono → whisper.cpp → видимая расшифровка → обычный запрос агенту`.

Расшифровка отправляется автоматически, как запросил владелец; при ошибке или пустом результате выполнение не начинается. Для v1: до 5 минут и до 20 MB, локальный timeout распознавания, один STT-процесс на экземпляр. Аудио удаляется после обработки или ошибки; оставшиеся после аварии файлы очищаются при запуске. Модель одна для всех экземпляров в пользовательском кеше, без дублирования в проектах.

Для сохранения порядка текст после голосового не обгоняет его во время STT. Слот очереди и session ID резервируются при получении voice update. Неуспешная расшифровка завершает этот слот ошибкой и освобождает очередь.

### Команды

| Команда | Контракт первой версии |
| --- | --- |
| `/start`, `/help` | Привязка владельца, справка, выбор агента |
| `/new` | Выбрать провайдера и создать новую сессию |
| `/sessions` | Список с пагинацией и выбор сохранённой сессии |
| `/rename <name>` | Поменять отображаемое имя Crowl, 1–80 символов |
| `/clear` | Создать пустую сессию того же провайдера; старую сохранить |
| `/status` | Проект, провайдер, сессия, запрошенный/применённый режим, выполнение, очередь |
| `/permissions` | Показать и изменить режим текущей сессии |
| `/stop` | Прервать активную задачу и приостановить выполнение очереди |
| `/queue` | Показать очередь, продолжить её или удалить ожидающие задачи |

`/new`, `/clear`, переключение сессии и изменение permissions не применяются, пока есть активная/ожидающая задача; бот предлагает сначала остановить работу и разобраться с очередью. Это исключает отправку старого промпта в новый контекст. `/rename` допустим во время работы. `/stop` обрабатывается вне очереди промптов, в том числе во время STT.

После `/stop` новый текст также не возобновляет очередь скрыто: бот предлагает `Продолжить очередь` или `Очистить очередь`. `/clear` не удаляет Telegram-переписку и не меняет файлы проекта. Неизвестная slash-команда возвращает справку, а не автоматически отправляется модели. Команды CLI агентов не обещаются как Telegram-команды.

`/model`, `/diff`, `/compact` и передача контекста между провайдерами — последующее расширение. До него используются модели по локальным настройкам CLI, а diff можно запросить обычным сообщением агенту.

## 4. Архитектура

```text
Telegram Bot API, long polling
             ↓
Проверка владельца и durable inbox
             ↓
Команды / очередь / STT
             ↓
Менеджер сессий и запусков ← SQLite
             ↓
ProviderAdapter
    ├── Codex app-server по stdio
    └── Claude Code CLI со структурированным выводом
             ↓
Родительская директория проекта

События адаптера → сохранение → Telegram renderer / outbox
```

Стек реализации: TypeScript со strict-проверками, Node.js 24, встроенные fetch/FormData, SQLite, util.parseEnv и node:test, структурированные логи с ротацией. grammY/zod/Vitest из первоначального предложения заменены стандартной библиотекой; причины зафиксированы в [ADR](docs/ADR-001.md). ORM и собственный агентный цикл не нужны.

Предлагаемая структура:

```text
src/
  config/       # .env, пути, проверки
  telegram/     # polling, auth, commands, callbacks, renderer
  core/         # sessions, runs, queue, lifecycle
  providers/    # types, codex, claude, capability checks
  storage/      # schema, migrations, inbox, outbox
  voice/        # download, whisper, cleanup
  service/      # lock, launchd, doctor
tests/
.data/          # локальная БД, lock, audio, logs; не в Git
```

Процессы запускаются через `spawn(binary, args, { cwd, env, shell: false })`; пользовательский текст передаётся через протокол/stdin, без конкатенации shell-команды. Родительская shell-сессия и её interactive PATH не требуются.

### Контракт провайдера

Обязательные операции: `probe`, `create`, `resume`, `send`, `interrupt`, `close`, `capabilities`. Смена режима выполняется между ходами, при необходимости через закрытие процесса и resume с тем же нативным ID. Никаких ложных успешных переключений.

Нормализованные события: `session.created`, `message.delta`, `message.completed`, `tool.started`, `tool.completed`, `input.required`, `run.completed`, `run.failed`, `run.interrupted`. Сохраняются и итоговый статус провайдера, и причина завершения процесса; exit code 0 сам по себе не доказывает успех задачи.

Codex: локальный `codex app-server`, handshake и протокол установленной версии; thread ID сохраняется сразу после создания. Использовать адресный resume, никогда «последнюю сессию». Обрабатывать ошибки/закрытие stdin/stdout и незнакомые некритические события. Не открывать сетевой listener app-server.

Claude: первоначальный кандидат — `claude -p` с `stream-json`, явным session ID/resume и штатной локальной авторизацией. Окончательный режим процесса и управление ответами на вопросы выбираются после короткой проверки CLI. Если CLI не обеспечивает нужное интерактивное управление, проверяем официальный Agent SDK и допустимую авторизацию. Не использовать недокументированные внутренние control messages без закрепления версии и контрактных тестов. Невозможность обязательного сценария — блокер этого адаптера, а не повод незаметно урезать требования.

Для обоих адаптеров нужны загрузка проектных инструкций и доступных локальных инструментов, сохранение окружения и штатная авторизация. Headless-режим не гарантирует полную идентичность интерактивному терминалу. Это проверяется на первом этапе; включение Claude `--bare` по умолчанию не подходит, поскольку меняет загрузку окружения и авторизацию.

### Разрешения

В первой версии обязательны два понятных профиля: `full` и `ask`. По умолчанию `full`. Нативные параметры конкретной версии отображаются в `/status`; разные провайдеры не выдаются за полностью одинаковые.

- Codex full: политика без запросов подтверждения и полный доступ sandbox, если локальная версия/управляемые настройки это допускают.
- Claude full: штатный bypass-режим; он не отменяет системные и отдельные обязательные правила провайдера.
- Ask: запросы инструментов выводятся владельцу с кнопками «Разрешить один раз» и «Отклонить». Ответ привязан к run ID и request ID; чужие, повторные и устаревшие callbacks отклоняются.
- Вопросы пользователя поддерживаются и в full: показываются текст/варианты и принимается ответ. Обычный промпт не должен случайно стать ответом на permission request.
- Ожидание ответа не блокирует polling или `/stop`. Через 10 минут запрос отменяется/отклоняется и ход завершается с явной причиной, если провайдер не допускает продолжение.

Состояния запрошенного и применённого профиля хранятся отдельно. Переход на более широкий режим применяется только после успешного подтверждения адаптером; отклонение политики провайдером показывается владельцу. `cwd` не является файловой песочницей при full access. Проверка Telegram-владельца обязательна независимо от permission profile.

Свободный ответ на вопрос принимается через Telegram Reply на конкретное сообщение бота. Permission request принимает только свои кнопки. Обычный текст без привязки остаётся промптом для очереди. Просроченные вопросы, остановленные runs и вопросы предыдущего процесса не принимают ответы; после восстановления их статус показывается явно.

## 5. Состояние и восстановление

SQLite хранит: metadata экземпляра и schema version; привязку bot ID/chat ID/user ID; сессии с provider ID; входящие updates; задания; события выполнения; исходящие итоговые сообщения; очередь вопросов/approvals.

Один активный run на экземпляр. Межпроцессная блокировка по каноническому пути не допускает foreground и LaunchAgent одновременно. Дополнительная пользовательская блокировка по bot ID предотвращает два poller с одним токеном в разных копиях на этом Mac. В `.data` сохраняется канонический путь проекта: скопированные состояния не принимаются молча за новый проект.

Состояния run: `queued → preparing → running ↔ waiting_input → completed | failed | interrupted | unknown`. `preparing` включает STT. Отдельно хранится paused-состояние очереди.

Входящий update сначала попадает в durable inbox с уникальным `(bot_id, update_id)`, затем polling продвигает offset. Маршрутизация в job и изменение session state выполняются транзакционно. Повтор доставки не создаёт второй job. Вариант интеграции с grammY должен сохранять этот порядок, а не полагаться на offset в памяти библиотеки.

Перед передачей провайдеру run помечается как запущенный. При аварии посередине отправки результат может быть неопределённым: Crowl не обещает exactly-once исполнение произвольных команд. Такие runs получают `unknown`, очередь приостанавливается, владельцу предлагается проверить файлы и продолжить явным сообщением. Автоматического повторного исполнения нет.

После перезапуска сессии доступны по сохранённым ID. Уже принятые, но ещё не начатые задания сохраняются; после незавершённого запуска ждут ручного продолжения очереди. Невозможность resume не создаёт чистую сессию молча.

Итоговые ответы проходят persistent outbox. Повторная отправка в Telegram разрешена с backoff; неоднозначный сетевой сбой может дать дубликат ответа, но не повтор задачи. Прогресс — best effort, итог сохраняется. Обрабатываются Telegram 429/retry_after, экранирование разметки и разбиение сообщений до лимита Telegram; длинные результаты отправляются текстовым файлом.

Renderer редактирует одно сообщение прогресса с ограничением частоты, первоначально не чаще раза в 2 секунды на чат. В Telegram выводятся доступные сообщения агента и краткие названия действий; внутренние reasoning-блоки не публикуются. Пока провайдер доступен, сбой доставки прогресса сам по себе не запускает задачу заново.

## 6. macOS и эксплуатация

Команды проекта: `npm start`, `npm run doctor`, `npm run voice:setup`, `npm run service:install`, `npm run service:uninstall`, `npm run service:status`. CLI-флаги и дополнительные варианты не нужны до работающего основного сценария.

LaunchAgent устанавливается под текущим пользователем без sudo, с уникальным label, абсолютными путями Node.js/entrypoint/working directory и явным PATH. Токены не в plist и не в аргументах: сервис читает `.env`. CLI binaries определяются установщиком и проверяются doctor; ошибки keychain/auth в background выводятся отдельно.

LaunchAgent стартует после входа пользователя. Автоматический старт до login после перезагрузки в первую версию не входит. FileVault и отсутствие login нельзя исправить пользовательским LaunchAgent. Установка и фактический тест login/restart обязательны на целевом Mac Mini.

SIGTERM останавливает приём новых задач, приостанавливает очередь, пытается прервать активный ход, закрывает дочерние процессы и БД. После timeout выполняется принудительная остановка принадлежащих Crowl процессов. PID проверяется с учётом времени запуска/владения, чтобы не завершить чужой процесс после переиспользования PID. Остановленные задачи не откатывают уже изменённые файлы. Отделённые агентом внешние сервисы не обещается полностью остановить.

Логи по умолчанию содержат технические события и ID без полных промптов, токенов, аудио и tool output. История в БД содержит пользовательские сообщения и ответы; владелец имеет локальный доступ к ней. `.env` и состояние создаются с ограниченными правами. Голосовые сообщения проходят через Telegram; локальная STT не делает транспорт end-to-end зашифрованным.

Обновление: остановить сервис → создать backup БД → обновить код и зависимости → миграция → doctor → запуск. Автообновление во время работы не нужно. Удаление сервиса оставляет `.env`/историю на месте. Перемещение проекта требует переустановки LaunchAgent.

## 7. План выполнения и критерии перехода

### Этап 0. Проверить самые рискованные интеграции

На локальных установках Claude и Codex в отдельном тестовом проекте проверить: prompt → изменение тестового файла → второй prompt с прежним контекстом → restart → resume; stream событий; full/ask; permission answer; вопрос пользователю; interrupt; загрузку проектных инструкций; авторизацию в background. Проверить whisper.cpp на русском с техническими английскими словами и выбранную версию Node/SQLite.

Результат: закреплённые версии, протоколы, таблица capabilities и краткий ADR. Если Claude CLI не закрывает ask/questions, решение об SDK принимается здесь. Нельзя строить весь продукт поверх непроверенного транспорта, а затем обнаружить отсутствие интерактивных запросов.

### Этап 1. Каркас и установка

TypeScript, lockfile, конфигурация, путь проекта, SQLite/migrations, process locks, doctor, `.env.example`, правила исключения локального состояния. `npm ci && npm start` работает в папке с пробелами и не зависит от cwd терминала. Неверный токен, отсутствующий CLI и неверный user ID дают понятные ошибки.

### Этап 2. Полный текстовый сценарий Codex

Telegram auth, durable polling/inbox, создание/сохранение сессии, Codex adapter, renderer/outbox. Критерий: из Telegram изменить тестовый файл в родительском проекте, получить ответ, задать второй вопрос с контекстом и продолжить после рестарта Crowl. Crowl не пишет результат задачи в собственный `src` вместо проекта.

### Этап 3. Claude и выбор провайдера

Claude adapter, кнопки выбора, нативные IDs и проверка отдельного контекста. Те же end-to-end сценарии, что для Codex. Отсутствие/ошибка Claude не переводит сообщение в Codex без явного выбора владельца.

### Этап 4. Управление сессиями и выполнением

Команды, FIFO, pause/resume/drop queue, stop, permission profiles и вопросы пользователя для обоих адаптеров. Критерий: режим действительно меняется, ответы приходят в правильный run, `/stop` доступен во время ожидания, сессии не смешиваются, неизвестная/прерванная задача не переисполняется автоматически.

### Этап 5. Голос

voice:setup, download, STT, порядок заданий, limits/timeouts, cleanup. Критерий: русское голосовое с техническим заданием отображается текстом и выполняется в активной сессии; следующий текст не обгоняет голос; сбой STT не запускает пустой промпт.

### Этап 6. Фоновая работа на Mac Mini

LaunchAgent, logs, shutdown, restart, duplicate protection. Критерий: закрытие терминала не мешает боту; после входа пользователя сервис доступен; остановка не оставляет активный агентный ход; два проекта с разными токенами работают независимо. Проверяется background-доступ CLI к авторизации.

### Этап 7. Приёмка и инструкция подключения

Пройти критерии ниже в двух тестовых проектах, затем подключить один реальный проект без изменения его бизнес-кода. Короткий README: требования, BotFather/user ID, две обязательные переменные, запуск, голос, сервис, troubleshooting, обновление и удаление. После успешной приёмки зафиксировать первый release/tag.

Порядок: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Каждый этап даёт проверяемый результат. Разработку начинаем с этапа 0; до него не фиксируем спорные детали транспорта как уже работающие.

## 8. Проверки и готовность

Автоматические проверки сосредоточены на последствиях сбоев: auth messages/callbacks; dedup updates; транзакционное создание job; очередь и session binding; voice ordering; resume по точному ID; stale approvals; CLI errors/partial JSON; Telegram 429 и длинные ответы; восстановление после kill. Для adapters используются записанные обезличенные протокольные fixtures, а не реальные платные запросы в CI.

Ручная приёмка на Mac Mini обязательна для обоих реальных агентов, STT и launchd. Успешные mock-тесты её не заменяют.

- [ ] Чистый clone в `.crowl`, установка и настройка без изменения package.json проекта.
- [ ] Текст работает с двумя Telegram-переменными, если CLI установлен и авторизован.
- [ ] Поддерживаются Claude и Codex, new/resume/clear/rename и выбор сессии.
- [ ] Агент работает в родительском проекте; пути с пробелами поддерживаются.
- [ ] Голос после документированной подготовки STT выполняется как текстовый запрос.
- [ ] Full/ask применяются и отображаются честно; вопросы/permissions имеют рабочий ответ.
- [ ] Queue/stop/restart не теряют принятые задания и не переисполняют неоднозначные задачи.
- [ ] Чужие сообщения и кнопки не запускают агента и не скачивают вложения.
- [ ] Крупные ответы и временный сбой Telegram не теряют сохранённый итог.
- [ ] Две копии в разных проектах не смешивают контекст и состояние.
- [ ] LaunchAgent работает после закрытия терминала и нового login пользователя.
- [ ] Секреты и локальная история отсутствуют в отслеживаемых Git-файлах.

## 9. Почему выбран этот вариант

Независимый процесс на проект даёт требуемую переносимость и не требует отдельного управляющего сервиса. SQLite нужна для очереди и восстановления; JSON-файл усложнит атомарность обновлений. Нативные интерфейсы двух агентов дают больше контроля над сессиями, чем терминальная эмуляция. ACP можно добавить позже без изменения Telegram-контракта.

Основные риски — не отправка текста в Telegram, а авторизация под launchd, интерактивные запросы Claude, граница отправки задачи при аварии и корректное прерывание процессов. Поэтому их проверка стоит перед полноценной реализацией. Несколько экземпляров full-access агентов разделяют пользователя macOS и не изолированы друг от друга на уровне ОС; переносимая папка — единица конфигурации, не контейнер.

## 10. Технические источники

- [Codex app-server](https://developers.openai.com/codex/app-server): сессии, события, lifecycle и permissions; точные схемы сверяются с локальной версией на этапе 0.
- [Claude programmatic execution](https://code.claude.com/docs/en/headless): структурированный вывод, resume и особенности завершения процессов.
- [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview): резервный путь интеграции с проверкой авторизации.
- [Telegram Bot API](https://core.telegram.org/bots/api): polling, update IDs, voice/file transport, лимиты сообщений.

Crowl реализуется как собственное небольшое ядро. Существующие мосты используются как референсы; копирование их кода и выбор форка не являются зависимостью плана.
