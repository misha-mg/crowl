# Одновременные сессии и эксплуатация на Mac Mini

Переключение между сессиями сохраняет выполняющиеся задачи. Лимит выполнения задаётся отдельно от выбранной сессии; безопасное значение по умолчанию — одна задача на общую рабочую папку.

## Выбор сессии и выполнение

`active_session` — фокус пользовательского ввода. Выполняющиеся задачи хранятся независимо в `Map<sessionId, ActiveRun>`. В одной сессии выполняется максимум одна задача; лимит проекта `MAX_CONCURRENT_SESSIONS` по умолчанию равен 1. Значения 2–16 явно включают параллельное выполнение в общей папке. Избыточные задачи остаются в сохранённой FIFO-очереди. Модель, native ID, permissions, pause и progress принадлежат своей сессии/run.

Новая сессия, чистый контекст и переключение не останавливают старую. `/stop` прерывает только выбранную задачу и ставит на паузу её очередь; `/close` отменяет задачи только закрываемой сессии. Выбор остановленной сессии с ожидающими задачами не снимает паузу. Явное продолжение — через `/queue`. Выбор пустой остановленной сессии позволяет начать новую работу без лишней паузы.

При лимите 1 переключение контекста не прерывает текущую задачу, а новая задача ждёт. При большем лимите сессии используют общую папку и Git index, поэтому изменения файлов и Git-операции нужно согласовывать заданиями. Startup и doctor сообщают о включённом параллельном режиме. Worktree-изоляция не реализована; существующий `.env` с явным лимитом 4 сохраняет своё поведение.

## Telegram и адресация

Каждый job сохраняет исходный message ID для внутренней адресации. Исходящие сообщения обычные, без Telegram Reply к заданию. Распознавание и прогресс обновляют одно сообщение, которое заменяется итогом; отдельная расшифровка не отправляется. Статус «печатает» обновляется каждые четыре секунды во время работы и не продлевается при ожидании владельца. Добавочная строка с provider/session ID не нужна.

`message_sessions` связывает пользовательские и исходящие сообщения с session ID. Reply к известному ответу/прогрессу направляется в ту же сессию независимо от текущего фокуса. Ответ на pending question/request обрабатывается прежде обычной маршрутизации. Для неизвестного Reply выводится инструкция вместо запуска неправильного агента. Привязки сохраняются после рестарта.

После пяти дней без новых updates polling проверяет сохранённые Telegram обновления с нулевого offset: это происходит до возможной смены последовательности идентификаторов после недельного простоя. Для новой последовательности сохраняются отдельные локальные ID и receipts, чтобы меньший Telegram ID не потерялся и повторная доставка не запустила задачу дважды. При обновлении старой базы без времени последнего update нулевой probe выполняется сразу; сохранённые идентификаторы сообщений и callbacks предотвращают повтор даже при совпадении старого и нового update ID. Эти идентификаторы сохраняются после очистки технических payload.

Обновления прогресса ограничены на весь чат и распределяются между runs. Очередь итоговых сообщений хранится отдельно. Постоянные ошибки доставки переводят запись в недоставленные, сохраняя текст и диагностику и освобождая следующие записи. Временные ошибки повторяются с задержкой; после 12 неудач без учёта rate limit сообщение также становится недоставленным. `outbox:status` читает диагностику без миграций, `outbox:retry -- ID|all` возвращает выбранные ответы в доставку. Закрытые вопросы и разрешения не повторяются. Повторная доставка никогда не запускает задачу агента повторно.

## Состояние и завершение

Схема SQLite 5 сохраняет адресацию версии 4 и добавляет диагностику доставки, временные метки и индексы ожидающих записей. Старые user message IDs восстанавливаются из inbox, где они доступны; старые исходящие ID, которые прежняя версия не сохраняла, не выдумываются. Перед обновлением существующей БД создаётся отдельный snapshot `before-migration-v*.sqlite`; все изменения схемы и данных затем фиксируются одной транзакцией. Резервное копирование работает online через read-only соединение и не запускает миграции до копирования.

Обработанные payload inbox и отправленные записи outbox очищаются после 30 дней порциями при старте и ежечасно. Идентификаторы обработанных updates остаются для дедупликации. Сессии, задания, результаты, привязки Reply и закрытые запросы сохраняются; недоставленные ответы не очищаются автоматически. Эта политика уменьшает технические копии истории без потери контекста и защиты от повторного выполнения.

При аварии только затронутые сессии получают unknown и паузу. Остальные могут продолжать работу. При остановке процесса Crowl сначала посылает abort всем агентам и только затем сохраняет pause: неисправная/заполненная SQLite не должна оставлять дочерние процессы работающими. Waiter promises также завершаются независимо от ошибок хранения. SIGINT/SIGTERM отменяют незавершённые проверки CLI.

Supervisor различает остановку владельцем и отмену соседних циклов после аварии. Фатальная ошибка сохраняется в диагностике и приводит к ненулевому exit code, даже если позже поступил SIGTERM. Версия пакета и fingerprint исходников выводятся при запуске, в `doctor` и `app:version`; fingerprint не читает секреты и состояние.

`InputBroker` отвечает за подтверждения, вопросы, таймеры и отмену ожидания. `scheduler.ts` выбирает допустимые задачи без I/O, `job-state.ts` проверяет переходы состояний, `migrations.ts` управляет схемой. Engine использует методы Store вместо прямого SQL; сохранение ответа владельца предшествует передаче ответа процессу агента.

## Голос и фон

Один экземпляр Crowl использует отменяемую FIFO STT-очередь, чтобы параллельные сессии не запускали несколько Whisper одновременно. Текст других сессий продолжает выполняться. Ошибки загрузки, включая ошибки потока body, редактируются для удаления Telegram-токена.

Сервис launchd запускает Crowl без Terminal и может создавать новые сессии по Telegram-команде. Install/start/stop/restart/status идемпотентны, блокировки предотвращают второй poller. Автозапуск действует после login пользователя. Реальная установка и тест после login требуют освобождения текущего foreground-процесса и доступа к пользовательской Library.

Для второго проекта используется чистая установка с новым токеном бота. Ключи, история, node_modules и работающие процессы первого экземпляра не копируются. Два бота/LaunchAgent имеют разные пути, блокировки и состояние.
